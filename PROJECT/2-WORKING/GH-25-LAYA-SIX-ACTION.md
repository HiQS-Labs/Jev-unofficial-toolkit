## Recon map

```text
Pinned holdout + baselines
  -> receipt-local prepare (same state/instruction/options; untracked JSONL)
  -> Laya Router.route (must select english for all 100 rows)
  -> Router.load(exact local snapshot) -> Agent.system_one
       -> common.build_sequence (512 max / 192 head; right-side state truncation)
       -> DecisionModel marker logits -> temperature -> option probabilities
  -> create-only raw JSONL outside Git
  -> receipt-local summarizer
       -> jev.eval.metrics / confidence_table
       -> jev.guard.write_results
  -> independent aggregate verifier
  -> committed typed receipt without source text or local paths
```

Material seams:

- `laya/router.py::Router.predict` calls `route`, `load`, then `Agent.system_one`; default routing selects the English root checkpoint for English Latin text.
- `laya/agent.py::Agent.__init__` downloads one filtered snapshot, loads config/tokenizer/encoder/weights, and uses float32 on CPU. The public loader has no revision parameter, so the run will pre-download the exact revision and pass its local snapshot directory.
- `laya/agent.py::Agent.system_one` produces choice/probabilities/confidence and input-token usage. It rounds probabilities to four decimals; the receipt uses an explicit rounding tolerance and labels confidence according to Laya's own entropy-derived semantics, not as independently calibrated.
- `laya/common.py::build_sequence` places question/options before state with `max_len=512`, `head_max_len=192`, and default `truncate_left=False`; overlong state keeps its beginning. The scorer will record full/used state-token counts and the receipt will state how many rows lost late context.
- This repository already owns metrics in `jev/eval.py` and create-only text-denylisted result writing in `jev/guard.py`. The published SemIf runner is a frozen pattern reference and must not be modified because its provenance pins its bytes.

Graph coverage was current with no recorded gaps for the Laya agent/common/router paths, their relevant tests, the SemIf receipt pattern, and the shared Jev metric/writer seams. This is best-effort coverage, not proof of completeness.

## Design decision

Ranked alternatives for the load-bearing model path:

1. **Selected — Router-selected root English checkpoint from an exact local snapshot.** This follows the documented recommended path while making revision pinning possible despite `laya.load` lacking a revision argument.
2. Direct `Agent` on the root checkpoint. It would produce the same model path but would skip evidence that the recommended Router actually selects it for every row.
3. `laya-typed-decisions`. It may be stronger on typed workflows, but this custom question does not match Laya's opt-in workflow IDs and selecting it would be a hand-picked alternate checkpoint, not the default routed arm.
4. Raise `max_len` / `head_max_len` or shortlist. That may preserve more state, but it changes the shipped default after observing a known limitation and belongs only in a separately registered follow-up.

Strongest counterargument: the typed-decisions checkpoint is arguably the semantically closest model. The reason not to use it here is reproducibility of Laya's default recommended behavior, not a claim that the root model is Laya's best achievable scorer. The receipt must make that distinction explicit. This is the main open question for plan QA.

## Closed evidence contract

The one Laya question ID is `next_action`. The runner constructs exactly this ordered public object; no alternate wording, criteria representation, or option ordering is accepted:

```python
{
    "next_action": {
        "type": "choice",
        "instructions": QUESTION,
        "criteria": {
            "edit": "Edit or create source files.",
            "git": "Inspect or change Git state.",
            "read": "Read files or command output.",
            "run_command": "Run a shell command not covered by another label.",
            "run_tests": "Run tests, linters, or a build verification.",
            "search": "Search code or find files.",
        },
    }
}
```

The order-bearing canonical representation stores criteria as the six `[label, description]` pairs above and has SHA-256 `6a268fefffc807cb1013765c5e23e9b668326f69704c0a65389989e7ca2f8edb`. A tokenizer-only preflight reproduces `build_sequence`: it compares the full `choice question: ...` token IDs with the used instruction slice and each full rendered option token list with its used slice after the 48-token and shared `head_max_len` rules. Every instruction and option must satisfy `full == used`; any loss aborts before `Agent` construction. State full/used counts remain separately measured per row because default right-side state truncation is permitted and disclosed.

Exact tracked write set:

- `evidence/2026-09-22-laya-six-action/{laya_next_action.py,README.md,results.json,provenance.json,verification.json}`
- `tests/test_laya_evidence.py`
- `README.md`, `ROADMAP.md`, and this task document

- `verification.json` has exactly `schema`, `valid`, `rows`, `sequential_indices`, `holdout_sha256`, `raw_output_sha256`, `results_sha256`, `provenance_sha256`, `metrics`, `per_label`, `max_option_probability_buckets`, `confidence_buckets`, `route_counts`, `head_tokenization`, and `state_truncation`.

Nested aggregate shapes are also closed: `metrics` is exactly the existing `jev.eval.metrics` fields (`labeled_n`, `uncertain_truth_n`, `correct`, `raw_accuracy`, `macro_f1`, `confusion_labels`, `confusion`); `per_label` has all six label keys and each value has exactly `support`, `predicted`, `recall_correct`, `recall`; `prediction_counts` has all six labels including zeroes; each probability/confidence bucket has exactly `bucket`, `n`, `correct`, `accuracy`; `route_counts` is exactly `{"english": int}`; `head_tokenization` is exactly `instruction_full`, `instruction_used`, `options_full`, `options_used`, `truncated`; `state_truncation` is exactly `rows`, `truncated_rows`, `full_tokens`, `used_tokens`, with each token summary exactly `min`, `median`, `max`, `sum`; and `timing` contains only `elapsed_seconds` with that same four-number summary. All counts are non-negative integers, hashes are lowercase 64-hex strings, nullable recall is the only null, and every other metric/summary is finite numeric data.

The summarizer validates every raw row and constructs and validates the complete results/provenance objects in memory before either create-only file write. The independent `verify` command takes the frozen holdout, frozen baselines, prepared input, canonical raw JSONL, committed results, and committed provenance as explicit inputs. It independently revalidates all hashes and closed schemas, reconstructs every row's text-free prediction from holdout + prepared input + raw output, recomputes model consistency plus route/head/state/probability/confidence/timing aggregates, builds the complete expected results/provenance objects, compares them to the committed files, and only then constructs the closed create-only verification object. Thus `raw_output_sha256` is measured by the verifier rather than trusted from provenance. Source-bearing inputs remain outside Git; only their hashes and text-free projections are committed. Missing/extra keys, a changed binding hash, or any one-field raw/projection mutation fails with the applicable output absent.

Laya returns six independently rounded four-decimal probabilities. Valid rows therefore require `abs(sum(probabilities) - 1.0) <= 0.0003 + 1e-12`; `0.1667 * 6` is the concrete accepting edge. The vector order must equal `option_ids`; `choice` must be declared; `max_option_probability` must equal `max(probabilities)`; and the rounded probability at `choice` must equal that maximum. A rounded tie preserves Laya's native returned choice rather than recomputing first-argmax from the rounded vector.

## Risks, rollback, and non-goals

- MPS/kernel variability is avoided by explicit CPU/float32. A CPU resource failure stops the arm rather than silently changing device or checkpoint.
- Native 512-token truncation may remove late recent-action context. That is a measured property of this default arm, not grounds to tune context length after seeing results.
- Request/model/source drift is controlled by the complete prepared-input hash, full commits, all downloaded snapshot hashes, and a pre-import eight-file manifest for the entire installed top-level Laya Python package; a mismatch stops the run before any Laya import or Router construction.
- Rollback is deletion of the additive receipt/runner/test and documentation pointers. No runtime API, schema, dependency, or production behavior changes.
- Non-goals: Laya source changes, integration adapter, tuning, calibration fitting, context-budget changes, shortlisting, alternate checkpoint/model sweep, Jev/SemIf rerun, private data, deployment, or broad capability claim.
- Any unexpected execution failure follows `/debug-mantra`: reproduce the exact row/run, trace the failing call path, run the cheapest disproof, and record every probe before changing the frozen arm.
